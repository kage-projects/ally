# Ally Dashboard

Next.js application for the Ally judge dashboard. Checkout lives in shopee-clone/ and the React SDK lives in sdk/.

## Run locally

From the repository root:

```bash
pnpm dev
```

Open `http://localhost:3000/dashboard`.

Development output is isolated in `dashboard/.next-dev`; production builds use
`dashboard/.next`. This allows `pnpm build` to run without overwriting an active
dev server's manifests and causing HTTP 500 responses.

The dashboard starts empty and listens on `BroadcastChannel("ally")`. A valid v1
event changes the status to **Live**; 15 seconds without a valid event changes it
to **Idle** while retaining session data. Heartbeats are optional. Status uses the
local receive time, so old producer timestamps do not make a fresh event look idle.

## Try the event stream

1. Open `/dashboard` in one tab.
2. Open `/dashboard/simulator` in another tab on the **same origin and browser profile**.
3. Click **Replay sample session**, or send each event individually.
4. Watch signals, profile, decisions, Keep/Undo, and the active adaptation update.
5. Wait 15 seconds to see Idle, then send another event to return to Live.
6. Use **Reset session** in the simulator to clear the receiving dashboard.

The simulator sends synthetic fixture events with fresh timestamps and unique IDs.
It is a development tool, not the checkout SDK or evaluation harness. Events are
ephemeral: open the dashboard before sending them. Cross-device/tab-profile sync
is outside this local channel's scope.

**Load demo** displays a local sample session without claiming a live connection.
The first live event clears that sample session before applying received data.
Sample evaluation numbers are shown only in explicit demo mode. Live mode shows
validated measured results or a clear pending/invalid state.

## Decisions and session impact

Decision filters include Rule, LLM, and Fallback. **View details** opens a native
dialog with the explanation, explicit guardrail results, source, lifetime, and all
changed token/layout/assistance settings. If the previous plan is unknown, the
dialog lists requested settings without inventing prior defaults. Escape or Close
returns focus to the trigger; a remote reset returns focus to dashboard content.

The baseline retains up to six windows and freezes at the first applied decision.
Adapted metrics use up to six complete windows recorded under an active
adaptation. Windows spanning an apply/undo transition and windows without an
active adaptation are excluded. Existing clean adapted samples stay visible.
Tap rate and targeting time are weighted by taps; targeting time is unknown when
there are no taps. Error loops are normalized per 10 seconds so different window
durations remain comparable. Worsening, unchanged, and missing data have distinct
labels instead of being displayed as improvements.

## Measured evaluation

Place actual evaluation output at repository-root `eval/results.json`, following
`EvaluationResults` in `contracts/dashboard.ts`. The reader requires
`schemaVersion: 1`, `isMock: false`, a valid `generatedAt`, a positive integer
`sessionsPerVariant`, and all four metrics with finite means and standard
deviations. Percent metrics use percentage points from 0–100. No result numbers
are generated by the dashboard.

The panel displays Ally off/on mean ± SD, sample size, scenario, and provenance.
`GET /api/ally/evaluation` re-reads the fixed file with `private, no-store` caching;
the browser refreshes every 15 seconds and offers **Refresh results**. Missing,
invalid, unreadable, or oversized files produce explicit unavailable evidence.
Transport errors keep the last loaded state with a visible refresh error.
Refresh requests time out after 8 seconds, including a stalled response body,
so a hung connection cannot leave the refresh action permanently busy. A newer
refresh or component unmount cancels the pending request.

If `eval/results.md` also exists alongside validated measured JSON, **View full
results** opens `/api/ally/evaluation/results`. Otherwise that endpoint returns
404 and the link is absent. Neither endpoint accepts a user-selected file path.
The Next.js tracing configuration includes these fixed files when present at
build time; hosted read-only deployments need a new deployment to update them.
See `eval/README.md` for the producer handoff.

## Integration contract

The provisional v1 contract is in `contracts/dashboard.ts`. Incoming events
are validated before reaching the reducer; unknown versions, invalid nested
fields, extra fields, and non-finite numeric values are ignored. Development
warnings omit the rejected payload. Event IDs are deduplicated within a bounded
500-event window. The dashboard retains at most 30 summaries, 100 decisions, and
six windows per comparison group. Local **Reset view** clears only this view and
keeps its listener open; a bus `reset` clears every listening dashboard.

Checkout producers and the dashboard share this versioned wire contract. Coordinate
SDK adapters with `sdk/src/schema.ts` without changing v1 payloads silently. No form values, screen content, or device identifiers belong in events.

## Quality checks

```bash
pnpm typecheck
pnpm lint
pnpm test:dashboard
pnpm build
```

`test:dashboard` uses the existing TypeScript compiler and Node's built-in test
runner (Node 24 recommended for the Windows test-file glob). It covers validation, reducer lifecycle, memory bounds,
connection timing, cleanup, unsupported browsers, and real channel delivery using
two Node channel instances.

The suite currently contains 45 tests, including decision diffs, direction of
metric changes, complete adaptation windows, zero-tap handling, measured-results
validation, file loading, and missing/report error cases. No new dependencies
are required. Client refresh tests also cover HTTP 500, invalid JSON/evidence,
network failure, timeout, and lifecycle cancellation.

Phase 2 browser verification (2026-11-07): Playwright exercised the dashboard and
simulator in two same-origin tabs. The 11-event replay rendered both decisions
with Kept/Undone states; 15 seconds of silence showed Idle; remote reset restored
Live and cleared the view; the next live heartbeat replaced local demo data.
The unavailable-channel fallback and demo loading passed without browser errors.
The dashboard was inspected at 1440px; no horizontal overflow occurred at 768px.
These checks use synthetic events; checkout SDK integration and real evaluation
results remain separate phases.

Phase 3–6 implementation checks: primary body/data text is at least 16px,
secondary metadata 14px, and key outcome values 28px. Flat grid separators and
the dark palette are retained; text contrast was checked against the background.
Current browser access is unavailable, so fresh screenshots at 1920×1080,
1366×768, and narrow widths plus native-dialog keyboard interaction remain a
manual verification gate. Actual checkout rehearsal and measured evaluation
output also require the checkout SDK/evaluation producer.
